## Summary

The Tamer-Studio database layer spans 20 schema modules in `src/lib/db/schema/` defining approximately 86 unique tables across auth, identity, billing, commerce, support, notification, asset, analytics, audit, CMS, landing, localization, email, feature flags, AI providers, jobs, and workflows. A stale duplicate schema exists at `drizzle/schema.ts` and `drizzle/relations.ts` containing only auth + admin tables (7 tables). 32 migration files exist (`drizzle/0000` through `drizzle/0031`). While the majority of the schema is well-structured with proper indexes and some foreign keys, there are 7 missing foreign key constraints, inconsistent soft-delete patterns across modules, and 18+ tables that lack any dedicated repository abstraction — all of which present data integrity and maintainability risks.

## Issues Found

### CRITICAL

1. **Missing FK: `wallet.workspaceId` → `workspace.id`**
   - File: `src/lib/db/schema/billing.ts:8`
   - `workspaceId` is declared as `text("workspace_id").notNull()` with no `.references()` call
   - Orphaned wallet records can exist after workspace deletion

2. **Missing FK: `creditTransaction.workspaceId`, `creditReservation.workspaceId`, `usageRecord.workspaceId` → `workspace.id`**
   - File: `src/lib/db/schema/billing.ts:30`, `billing.ts:52`, `billing.ts:76`
   - All three tables reference `workspaceId` without foreign key constraints
   - Orphaned billing records post-workspace-deletion is a financial data integrity risk

3. **Missing FK: `order.workspaceId` → `workspace.id`, `order.userId` → `user.id`**
   - File: `src/lib/db/schema/commerce.ts:8-9`
   - Order table references both workspace and user without FK constraints
   - Critical for commerce data integrity

4. **Missing FK: `cmsPage.authorId` → `user.id`**
   - File: `src/lib/db/schema/cms.ts:38`
   - `authorId` is `text("author_id").notNull()` with no FK constraint
   - CMS pages can reference non-existent users

5. **Missing FK: `cmsVersion.authorId` → `user.id`**
   - File: `src/lib/db/schema/cms.ts:160`
   - Same pattern — author reference without FK

6. **Missing FK: `cmsAuditEntry.authorId` → `user.id`**
   - File: `src/lib/db/schema/cms.ts:214`
   - Audit trail author references have no referential integrity

7. **Missing FK: `refund.paymentIntentId` → `paymentIntent.id`**
   - File: `src/lib/db/schema/commerce.ts:247`
   - `paymentIntentId` is `text("payment_intent_id").notNull()` with no FK constraint
   - Refunds can reference non-existent payment intents

### HIGH

8. **Stale duplicate schema at `drizzle/schema.ts` and `drizzle/relations.ts`**
   - `drizzle/schema.ts` contains 7 tables (verification, account, session, failedLoginAttempt, user, admin, adminSession)
   - `drizzle/relations.ts` defines relations for only these 7 tables
   - These are auto-generated by drizzle-kit but contain only the initial migration subset — 80+ tables are missing
   - Risk: confusion about which schema is canonical; potential drift if the wrong file is imported

9. **Inconsistent soft-delete pattern**
   - `cmsPage` uses `deletedAt` (`src/lib/db/schema/cms.ts:39`)
   - `supportTicket` uses `deletedAt` (`src/lib/db/schema/support.ts:26`)
   - `supportKnowledgeArticle` uses `deletedAt`
   - `userProfile` uses `deletedAt` + `deletedBy` (`src/lib/db/schema/identity.ts:19-20`)
   - Most other tables (billing, commerce, CMS sub-tables, etc.) use hard delete or have no pattern
   - No global convention — different modules follow different approaches

10. **18+ tables without dedicated repository classes**
    - Tables lacking repository abstractions: `failedLoginAttempt`, `admin`, `adminSession`, `billing`, `job`, `queue`, `workflow`, `workflowExecution`, `featureFlag`, `featureFlagHistory`, `aiProvider`, `aiProviderModel`, `asset` (7 tables), `productionMetrics`, `userActivityMetrics`, `workspaceMetrics`, `eventQueue`, `emailProvider`, `emailProviderHealth`, `emailQueue`, `emailLog`, `emailStatistics`, `emailTemplate`, `emailToken`, `costRecord`
    - All of these are accessed via direct `db` calls (see repository-validation-report.md)

### MEDIUM

11. **`billing-admin.ts` schema defines `billing` table separate from `billing.ts`**
    - File: `src/lib/db/schema/billing-admin.ts`
    - Creates a second billing module file — potential confusion about which file is authoritative

12. **Missing FK: `subscription.workspaceId` → `workspace.id`**
    - File: `src/lib/db/schema/billing.ts:129`
    - While `workspaceId` has a unique constraint, it has no FK to workspace

13. **Missing FK: `invoice.workspaceId` → `workspace.id`**
    - File: `src/lib/db/schema/billing.ts:152`
    - Invoice workspace reference lacks FK

14. **Missing FK: `supportTicket.workspaceId` → `workspace.id`**
    - File: `src/lib/db/schema/support.ts:12`
    - `workspaceId` is nullable (`text("workspace_id")`) without FK

15. **Missing FK: `usageRecord.userId` → `user.id`**
    - File: `src/lib/db/schema/billing.ts:75`
    - Nullable but still no FK constraint

### LOW

16. **No migration for CMS author FK constraints**
    - Migration `0031_create_cms_tables.sql` exists but the FK constraints for `authorId` were not included in the table creation

17. **`landing.ts` schema tables (`landingSection`, `landingMedia`) appear to duplicate CMS functionality**
    - File: `src/lib/db/schema/landing.ts`
    - These overlap with `cmsSection` and `cmsMedia` — potential confusion about which is the source of truth for landing page content

## Compliance

**FAIL**

The database schema fails CMS-01 Finalization due to:
- 7 missing foreign key constraints on critical cross-module references (billing, commerce, CMS)
- Stale duplicate schema files at the drizzle root that could cause confusion
- Inconsistent soft-delete patterns with no documented convention
- 18+ tables lacking repository abstractions, leading to direct DB access scattered across 18+ service files

Resolution of all P0 items (missing FKs) is required before passing compliance. P1 items should be addressed in the same sprint.
